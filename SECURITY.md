# Security and Privacy Policy

Security and user privacy form the core foundation of Oath Light. Oath Light delivers robust content filtering and tamper resistance without invading personal privacy, tracking online activity, or uploading visual data to remote systems.

---

## Core Security and Privacy Guarantees

* **Zero Telemetry and Complete Isolation**: Oath Light collects zero user metrics. The application operates entirely on your local machine with no remote logging endpoints, tracking scripts, or analytics services.
* **100% Local Machine Learning Execution**: Screen inspection models (SigLIP2 5-class vision transformer and NudeNet ONNX) run locally on host hardware using `ort` (ONNX Runtime). Display frames are processed directly in GPU/RAM memory and immediately discarded.
* **Cryptographic Verification**: Software updates, password hashes, and event logs utilize cryptographic standards to protect system state against unauthorized tampering.

## Security Architecture and Cryptographic Foundations

Oath Light uses specialized cryptographic primitives across its Rust subsystems to ensure security and data isolation.

| Security Component | Subsystem Location | Underlying Primitive / Technology | Operational Security Role |
| :--- | :--- | :--- | :--- |
| **Master Password Protection** | `desktop-app/src-tauri/src/auth.rs` | Argon2id Key Derivation (`argon2`) | Secures weakening requests using salt strings generated by `rand_core::OsRng`. |
| **OTA Update Verification** | `desktop-app/src-tauri/src/ota.rs` | Ed25519 Digital Signatures (`ed25519-dalek`) | Verifies signed blocklist manifests against embedded public keys in `core`. |
| **Hash-Only Frame Log** | `desktop-app/src-tauri/src/evallog.rs` | SHA-256 Hashing (`sha2`) | Logs SHA-256 hashes of screen frames without saving visual thumbnails or URLs. |
| **Event Log Tamper Proofing** | `core/src/eventlog.rs` | Cryptographic Hash Chain | Maintains sequential event records bound by SHA-256 hash chaining. |
| **Dual Watchdog Mutexes** | `watchdog.rs` and `guardian` | Win32 Kernel Mutex Primitives | Cross-monitors `OathLight.Watchdog.Main.v1` and `OathLight.Watchdog.Guardian.v1`. |

## Threat Model and Mitigation Matrix

The table below details how Oath Light mitigates potential security risks, bypass attempts, and unauthorized modifications.

| Threat / Attack Vector | Risk Description | Oath Light Defensive Mitigation |
| :--- | :--- | :--- |
| **Process Termination** | User or script attempts to kill application processes via Task Manager. | Dual watchdog architecture (`OathLight.exe` and `oathlightguard.exe`) cross-monitors mutexes and immediately resurrects killed processes. |
| **System Clock Manipulation** | User rolls system clock forward to expire active cool-off timers. | Boot-anchored monotonic counter (`std::time::Instant`) measures hardware cycles, freezing timers and logging clock anomalies. |
| **Local Settings Modification** | User edits configuration JSON files directly on disk. | Mandatory enforcement floor (`settings::force_mandatory`) validates settings on launch and reinstates safety baselines. |
| **Unauthorized Uninstallation** | User executes setup uninstaller to bypass active filtering rules. | CLI gate (`--uninstall-check`) intercepts uninstallation attempts and enforces cool-off delay or Argon2id master password verification. |
| **DNS-over-HTTPS (DoH) Bypass** | Browser or application uses encrypted DoH resolvers to bypass local DNS. | Local proxy (`oathlight-dns`) blocks known DoH endpoint IPs and enforces enterprise browser policy settings. |
| **Network Interface Reset** | Network adapter state changes cause loopback DNS failure. | Isolated RFC 6761 health probe (`health-probe.oathlight.invalid`) verifies listener health and safely restores settings via `dns.json`. |

## Data Isolation and Local Audit Summary

To verify our privacy claims, the table below outlines all local storage locations used by Oath Light. Zero bytes of data leave the machine.

| Data Type | Storage Location | Privacy Standard & Lifecycle |
| :--- | :--- | :--- |
| **Frame Evaluation Records** | Local Memory (`evallog.rs`) | Stores only SHA-256 frame hashes; zero thumbnails or URLs ever saved. |
| **Application Configuration** | `%APPDATA%\OathLight\settings.json` | Stores local preference flags; protected by mandatory enforcement floor. |
| **DNS Adapter Backup** | `%APPDATA%\OathLight\dns.json` | Backs up original network adapter settings for safe teardown restoration. |
| **Event Audit Log** | `%APPDATA%\OathLight\eventlog.db` | Local SHA-256 hash-chained log documenting protection events. |
| **Machine Learning Models** | Embedded Binary / Local Storage | SigLIP2 and NudeNet ONNX models execute 100% offline in RAM/GPU memory. |

## Responsible Vulnerability Reporting and Disclosure Policy

We welcome independent security research, vulnerability analysis, and responsible bug disclosure.

### Critical Vulnerability Disclosure Notice

> [!IMPORTANT]
> If a critical security vulnerability, severe bypass flaw, or remote exploitation vector is identified, **it must NOT be discussed, published, or disclosed in public forums, public GitHub issues, or social media**.
>
> All critical security issues and zero-day vulnerabilities must be referred directly and privately to the lead developer by emailing **abdelhamidalielsebaie@gmail.com** or submitting a private GitHub Security Advisory.

### Reporting Guidelines and Requirements

Please include the following technical details in your private disclosure email:

* Affected component or crate (e.g., `oathlight-dns`, Tauri IPC bridge, `browser_lock.rs`, extension interceptor).
* Complete reproduction steps or proof-of-concept exploit code.
* Observed security impact and suggested remediation path.

Private reports receive a direct acknowledgment within 24 to 48 hours, followed by prioritized security patches.
